# 目录职责与维护规范

## 仓库与应用

| 路径 | 职责 | 维护要求 |
| --- | --- | --- |
| 仓库根目录HTML、原使用说明 | 1.0历史原型 | 保留追溯，不作为2.0入口 |
| .github/ | CI、代码扫描、PR和依赖策略 | 保持最小权限与Action固定提交 |
| opo-2.0/frontend/ | 当前模型、管理、会员支付及旧沙盒页面 | 明确页面属于哪一套模型，生产权限不在浏览器判断 |
| frontend/assets/ | 页面脚本、样式、业务模拟模块和静态资产 | 按模块扩展，不另建平行重复页面 |
| backend/ | 已有服务端沙盒与基础设施 | 含旧规则；与最新前端尚未完整集成，不能直接生产启用 |
| config/ | 已批准参数、示例与门禁 | 与计算代码和测试共同审查，不放凭据 |
| database/ | schema及数据库相关文件 | runtime本机数据不进Git |
| integrations/ | 外部服务接入边界 | 占位/未接入需明确，不伪造成功回调 |
| scripts/ | 预览、检查、备份、接续及运维工具 | 无隐式部署、无静默覆盖数据 |
| tests/ | 业务回归与浏览器验收 | *.test.mjs为单元/集成；*-browser.mjs等为场景验收 |
| deployment/ | 环境部署模板 | 不写真实凭据，按环境复核 |
| maintenance/ | 维护资料和运维支持 | 与生产操作权限区分 |
| docs/ | 可公开的规则、技术交接、操作和部署文档 | 新文档登记索引，历史版本标清 |

## 新文件如何放

业务模块沿用上述归属；测试放tests，静态产品资产放frontend/assets/products；公开文档放docs并登记。截图/临时测试结果放被忽略的test-results，运行库放database/runtime。密钥、客户导出、付款凭证与内部记录存私有位置。不要将完整源码ZIP、运行数据库或电脑路径复制进仓库。

现有大文件逐功能渐进拆分：先建立行为测试，再提取纯计算/状态模块，最后减少总入口责任。每次只处理明确功能，避免“大重构”同时改规则和目录。
