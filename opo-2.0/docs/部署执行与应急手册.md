# OPO部署执行与应急手册

日期：2026-10-17。**本轮停止部署，以下操作仅供恢复部署后执行。** 当前本地测试通过不等于正式服务器验收；Docker、Caddy、systemd、DNS、HTTPS均未在目标主机验证。

## 1. 交接与边界

首期只能启用`OPO_MODE=catalog`。保留空商品目录、三语浏览、咨询与管理员处理；不得以sandbox替代catalog公开，不开启资产功能。域名候选opo3market.com，预算30美元/月，实际报价、税费和用量仍需核对。服务器区域候选新加坡。当前未注册域名、未创建服务器、未支付。

恢复时先核对准备包SHA256、源码提交和清单；确认实际操作只涉及OPO新资源，不影响其他项目。账户由用户正常登录，密码、验证码、私钥不要交到聊天或仓库。服务器维护人、咨询处理人、数据请求联系人和备用恢复人应明确；OPO是显示名称，不替代实际责任信息。

## 2. 正式主机执行顺序

1. 取得域名与云账号控制权，开启账号MFA、账单提醒与域名续费提醒。按实际购物车核算域名年费、服务器、备份、存储、税费；30美元是预算，不是平台自动硬限额。
2. 创建最小候选主机；配置SSH密钥、系统更新、时间同步、防火墙。仅公开80/443，SSH限制来源；3200与数据库不得对公网开放。备份凭据权限单独限制到OPO备份路径。
3. 选择Docker或裸Node一种运行方式。核对现有`compose.yaml`、`deployment/compose.catalog.yaml`和Caddyfile。执行`docker compose --env-file .env.catalog -f compose.yaml -f deployment/compose.catalog.yaml config --quiet`；通过后再构建。检查Node 24.18.1、镜像来源、实际数据卷与非root权限。当前机器无Docker，以上步骤未执行。
4. 从`.env.catalog.example`复制私有环境文件，配置准确HTTPS origin、OPO、客服邮箱、30天咨询保留时间、实际反向代理IP。只信任已验证代理地址，不能填任意网段或盲用模板回环地址。环境文件限制读取，不提交Git。
5. 首次初始化前执行`npm run secrets:init`生成MFA加密密钥；另执行`npm run backup:key:init`生成备份加密密钥。两者用途不同，均需在服务器之外独立加密保管。已有数据库不可重新生成MFA密钥。Windows的mode参数不等于完整ACL保障，正式Linux权限仍须检查。
6. 在与运行服务相同的持久数据库路径和MFA密钥环境中执行`npm run bootstrap`，管理员密码通过临时进程环境安全输入，完成后清除；不得写入脚本、历史命令或文档。先保持仅本机可访问，完成管理员登录、认证器绑定及退出重登。初始化环境和Docker数据卷必须指向同一数据库，不能在宿主机另建一份误当正式库。
7. 本机执行`npm run catalog:readiness`，所有阻塞项清除后，再配置域名与HTTPS；检查apex跳转www、证书续签、代理来源与真实客户端限流。Caddy先用实际配置执行`caddy validate --config <实际Caddyfile路径>`。
8. 执行`npm run smoke:catalog -- https://www.opo3market.com`。该脚本只读，不证明咨询提交、MFA、持久化或异地恢复已通过。由操作者使用已同意的数据完成一次真实咨询→后台查看→状态处理；确认用户看到“已保存”，没有误称邮件已发。
9. 重启服务及主机后验证账户、商品与咨询仍在；完成异地备份恢复、外部告警触发和手机三语验收。将实际时间、版本、检查结果及未解决事项记入验收记录后，才可接受首期公网流量。

裸Node可参考`deployment/systemd/`三个模板。先验证`/usr/bin/node`、工作目录、opo用户、环境文件和读写权限；用目标机`systemd-analyze verify`核验再安装。模板默认每15分钟备份，未安装启用。不要与Docker并行操作同一个数据库；不要只启用timer却遗漏备份密钥及异地复制。

## 3. 备份、保留与恢复

本轮补齐SQLite一致性快照→完整性/外键检查→AES-256-GCM加密→SHA256证据。程序不负责云上传、轮转或监控，证据中的`remoteCopyVerified:false`必须如实保留。加密能防止未持钥者读取，不等于异地副本已存在。

在已授权的主机环境设置`OPO_DATABASE`、`OPO_BACKUP_KEY_FILE`、`OPO_BACKUP_DIR`后执行`npm run backup:encrypted`；输出`.opobak`和同名证据JSON。不要以普通`npm run backup`的明文文件作为可公开上传材料。Docker默认没有备份密钥挂载或专用备份目录；必须先按实际部署补齐只读密钥挂载和私有可写备份目录，再运行该命令，不能直接照搬systemd路径。

建议目标：最多丢失15分钟数据、4小时内恢复，仅在定时任务、异地复制和实测满足后才能承诺。业务确认备份生命周期，例如短期备份7天、每日备份30天；这是待确认策略，尚无自动轮转实现。咨询保留30天不代表历史备份立即消失，隐私说明必须写清备份保留/限制使用/到期清理；身份请求与备份删除策略仍待完善。

异地恢复演练顺序：从异地下载加密文件及证据→核对SHA256→设置备份密钥→`npm run backup:decrypt -- <加密文件> <全新私有目录/restored.db>`→`npm run restore:check -- <全新私有目录/restored.db>`。程序拒绝覆盖目标，恢复检查使用隔离副本；它验证数据库及账本，不验证链上状态。检查过期咨询计数，在隔离环境执行到期清理，不能让恢复动作重新启用已过期记录。演练完清理临时明文及访问权限。

数据库恢复正常仍需使用独立保存的MFA密钥恢复认证器信息，验证登录和咨询读取。不能只备份数据库、把两个密钥也只放在同一台服务器。异地存储要限制公开访问；上传与轮转失败须触发告警。

## 4. 故障与回退

- 网站故障：先核对健康检查、磁盘、内存、进程、证书、代理和错误日志；禁止把环境变量或咨询正文贴入公开问题。
- 误配置/安全事件：限制公网访问或维护页，保留必要审计，撤销受影响会话与凭据，再调查修复。不要用开启sandbox来“临时恢复”公开服务。
- 发布失败：先停止写入并备份当前库，再核对迁移兼容性。旧代码可能拒绝新迁移版本，不能直接覆盖文件和数据库；优先用兼容新库的修复版本。确需配套旧库回退时，先明确会丢失哪些新增咨询，再决定恢复点。
- 密钥遗失：备份加密密钥遗失无法解密备份；MFA密钥遗失不能靠重新生成恢复原认证器。按事前验证的备用恢复流程处理，不在生产库中随意绕过管理员MFA。

## 5. 自动维护的实际边界

已有检查脚本、测试和CI能发现一部分回归；新增加密备份可定时运行，但当前没有正式机定时任务、外部监控或自动修复服务。今后可自动巡检、建修复分支、运行测试、生成待审PR和备份报告。资金规则、合约升级、密钥变更、数据库恢复及生产发布需要明确范围和验证；不能承诺AI无人值守解决所有故障。当前暂停指令同样禁止后台自动部署。
