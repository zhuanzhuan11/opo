# 首期商品展示与订单咨询：部署与验收

本页适用于用户2026-10-17确认的首期范围，不代表未来代币交易商城完成。模式为 `catalog`，不接受充值，不创建付款或订单，不开放认购、兑换、释放或奖励。咨询保存到本站收件箱，**没有自动发送邮件**。

## 已具备的应用流程

- 中英日商品目录、搜索、详情文字和商品咨询；无商品时显示空目录。
- 管理员登录、动态验证码、三语真实商品编辑/上下架、咨询查看及状态处理。
- 咨询仅收集邮箱、选填称呼和问题；明确经营主体、用途、保存周期和联系邮箱，要求主动勾选同意。
- 咨询接口防重、限流，其他用户无法读取收件箱；访客输入按文本显示。
- 到期咨询记录在启动及定时任务中清理；备份恢复后再次按业务记录有效期清理。备份本身仍须由运营方设置保存和销毁周期。
- 首期接口和页面白名单隔离；旧交易页面及充值/支付/认购/兑换接口均不可用。
- 不会把sandbox演示商品自动发布成正式商品；测试截图中的商品只存在内存测试库。

## 仍需项目方提供

1. 经营主体及公开客服邮箱，用于用户识别和咨询回复。
2. 真实商品三语资料及图片使用权；没有资料时可以保留空目录，不发布虚构在售商品。
3. 域名、托管账户/服务器位置、运行预算及必要的账号授权。不要在聊天提供密码或私钥。
4. 实际服务国家。英语不是国家；涉及跨境商品、隐私和后续资产服务时按国家确认。

## 本机配置及初始化

Node.js 24.18.1下执行 `npm run check`，准备私有持久数据库，按README初始化管理员。执行 `npm run secrets:init` 生成独立密钥文件。将OPO_MFA_KEY_FILE指向该文件，先在本机以catalog模式启动，通过 `/catalog-admin.html` 登录并绑定验证器。此时仅监听本机，允许尚未配置公开域名。绑定完成后再配置真实经营主体、邮箱和公开HTTPS来源。

设置OPO_MODE=catalog。配置字段见 deployment/.env.catalog.example；模板不包含真实密钥，也不会被Node自动加载。模板中的示例主体/邮箱/域名不能作为实际生产资料。

执行 `npm run catalog:readiness` 检查应用配置。该命令仅判断是否准备好部署，不会声称已上线，也不替代实际服务器验收。`npm run readiness`检查未来完整资金版，当前保持不通过属于预期。

## Docker部署候选

当前工具环境没有Docker，以下配置尚未实际执行验证：

```sh
docker compose -f deployment/compose.yaml -f deployment/compose.catalog.yaml up --build -d
```

Compose变量需由部署环境注入，或使用明确的 `--env-file` 指定不入库的本地配置。保持数据库卷持久化，MFA密钥单独保存。使用Docker时，应先运行默认sandbox Compose（仅绑定主机127.0.0.1），在同一持久卷内通过 exec 执行管理员bootstrap并在本机后台完成MFA绑定；随后停止sandbox服务，再以catalog覆盖文件重启，继续使用同一个opo-data卷。不要把另一个本机数据库已初始化误认为容器卷已初始化。完成后再向公网开放；默认容器主机绑定0.0.0.0时会检查公开HTTPS来源、经营主体、客服邮箱、MFA密钥及已绑定管理员，不满足则拒绝启动。

部署目录不得向外暴露数据库、备份或密钥。Node端口保持仅绑定主机回环地址，由反向代理提供HTTPS。示例Caddyfile只提供路由，不代表已申请域名或证书。OPO_TRUSTED_PROXIES必须填Node看到的真实代理IP；在Docker场景可能是桥接网关，不能盲目使用示例。只从这些代理解析转发来源，从右向左排除可信代理，避免伪造首个X-Forwarded-For。

## 上线验收

- 核对真实域名、HTTPS、正确经营主体及可用客服邮箱。
- 从外网确认首页/商品/咨询正常；支付、充值、认购及兑换路径均关闭。
- 管理员完成MFA登录，发布一条经核实的商品，再从未登录访客提交有同意记录的咨询；后台能查看和标记处理。
- 明确由运营人员查看收件箱并回复；仅填写邮箱不代表已有邮件通知服务。
- 验证不同访客限流不会因代理共用IP而误伤。
- 验证重启后商品、咨询和管理员配置保留；数据库及密钥不在网页可访问路径。
- 执行一致性备份和隔离恢复检查，配置异地加密备份、保存周期和告警渠道。
- 在实际主机核验运行日志、资源使用、监控与故障处理；本机Chrome及内存负载测试不能替代。

## 后续资产功能边界

用户确认的BSC公开地址保存于 config/chain-public.json，首期前台不显示收款/充值指引。

只读链上观察显示ZC及USDT均为18位精度，未发现DELEGATECALL/CALLCODE，常见EIP-1967槽为空。当前按“未发现常规代理升级入口的外部代币”接入，不承诺商城可以修改这两个代币。USDT的owner读取返回非零地址，不代表本项目拥有该权限。收款地址在查询时无合约代码，不能当作已配置的多签托管。

ZC在Sourcify未取得已验证源码，区块浏览器访问被拒绝，不能出具完整合约审计或绝对不可升级结论。未来自建业务合约需单独设计、测试并保留明确的代理/多签/升级路径，不能把更改前端当作升级链上规则。

技术验证通过也不自动取得各地业务准入：中国人民银行通知对相关虚拟货币业务有明确限制；日本金融厅对相关交换/中介等业务设有注册制度。具体业务需按实际经营方式审核，不能将“英语地区”整体视作允许区域。
