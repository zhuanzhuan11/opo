# 后续开发与上线顺序

当前可继续开发与演示，但不具备真实资金上线条件。以下为后续实施顺序，不是工期或已完成承诺。

| 顺序 | 工作 | 完成证据 |
| --- | --- | --- |
| 1 规则基线 | 将商品、支付、分佣、退款、资格、OPOC与ENI规则逐项核对；明确推荐产生OPOC的来源、金额及争议边界 | 版本化规则、示例订单和验收场景；未知项标待确认 |
| 2 服务端整合 | 清点旧backend与当前前端差异，设计正式会员身份、权限、订单/支付状态、金额账本、规则快照与迁移 | 接口契约、迁移/回滚方案、精度和权限测试 |
| 3 最小商户闭环 | 先一家商户、一种渠道、一次绑定；验证签名回调、防重、退款逆向、营销预算与现金确认 | 支付机构沙盒验收、逐笔对账、失败重试和责任方明确；模拟按钮不算支付接入 |
| 4 奖励与跨店 | 消费/一级推荐奖励、发行商户责任、跨店补偿、查询/争议/审计 | 账本守恒、无重复奖励、余额不足与退款追偿场景；国家/币种隔离 |
| 5 独立链上项目 | OPOC/ZC/ENI资产核验、定价、合约权限、库存、销毁、释放及链上事件恢复 | 明确资产可用性、真实测试网与独立审查；USDT兑付不因积分存在而开放 |
| 6 生产运维 | 目标环境、密钥管理、备份恢复、监控告警、权限/审计、容量及发布回滚 | 在目标环境执行恢复演练、故障演练、独立检查和上线批准 |

## 每次发布必须记录

来源Git提交、发布环境、部署版本、范围、实际运行检查、数据库迁移与备份、回滚版本、批准人及观察结果。代码推送成功不等于站点发布成功，演示站成功不等于生产验收。

## 持续维护

每次换设备先同步；每个变更更新最新技术交接。维护依赖与CI固定版本，定期做备份恢复和权限复核。发现线上问题先保全日志、定位影响、采取可回退修复；不能直接修改历史订单金额或吞掉对账差额。任何正式资金开关必须等真实缺项完成后另行审查，不绕过readiness。
